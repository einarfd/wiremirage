# ADR-0020: Shared wasm engine components for interpreted languages

**Status:** Accepted

- *2026-05-27 — half of the deferred engine optimisations landed, on this ADR's own terms.* The implementation order below deferred "the `Engine`-instance-cache and pre-parsed-bytecode optimisations ... until measurement says they're needed". Measurement said so, and `2289b34` shipped the **pre-parsed-bytecode** half: the StarlingMonkey component is Cranelift-compiled once and memoized as a serialized artifact, in-process in a `OnceLock` and on disk in the temp dir, both keyed by a hash of the engine bytes. Every `Runtime` builds its `Engine` from the same `Config`, so an artifact one compiles deserializes in any other; a stale artifact (after a wasmtime upgrade, say) fails `deserialize` and is transparently recompiled, so the cache is self-healing. The numbers that justified it, in debug: the 9-test `js_engine_dispatch` binary from ~210 s to ~40 s, and a single engine test from ~32 s to under a second once the process has compiled. Wasmtime's own on-disk compile cache was tried and rejected — its per-entry file locking serialises parallel test threads badly (8.5 s single-threaded against 124 s at default parallelism). **The `Engine`-instance cache remains deferred**: `Runtime::new` still calls `Engine::new` per instance, and sharing the artifact rather than the `Engine` was enough.

- *2026-09-02 — the source-pipeline description below had drifted from the implementation, and the drift was load-bearing.* Two corrections, recorded here because a user hit the consequence. First, this ADR said the host transpiles TS and **stores the resulting JS** on the `Route` record; the implementation stores the *author's original* source and derives the JS at dispatch, which is what makes `show_route_source` / `export_group` return what was written. Second, and the actual bug: `javascript` had been implemented as the literal reading of "already JS" — stored with no validation whatsoever and handed to the engine untouched. Because the engine evaluates source as a *script*, a JS handler written the way the docs document it (`export function handle`) was accepted by `create_route`, listed as healthy, and then returned 500 on every request; the identical source declared `typescript` worked only because that path happened to rewrite the export away with a literal string replace, which covered one spelling and silently missed `export default`, `export { handle }`, `export const handle`, and `import`. A route set could stand up, look correct, and serve nothing. Both languages now share one pipeline — validated through `wm-transpile` at create/patch time, original source stored, script-shape JS derived and cached at dispatch — and the export unwrapping is an AST pass rather than a string replace. The forms that are accepted and the forms that are a create-time `compile_failed` are specified in `script-api-wit.md`, under "Handler source shape". The invariant the fix is really about: **anything `create_route` accepts, runs.**

**Context:**

[0004-multi-language-via-sidecars.md](0004-multi-language-via-sidecars.md) picked "compiler as a separate container, called over HTTP" as the universal compile path. That decision is still right for **AOT languages** — TinyGo, Rust, Zig, C, AssemblyScript-when-emitting-wasm — where "compile" really does mean "produce a wasm module from source." A TinyGo handler compiles in single-digit seconds; the sidecar pattern earns its keep.

It is wrong for **interpreted languages** as implemented today. The TypeScript path goes through `componentize-js`, which bundles **StarlingMonkey** (SpiderMonkey-on-wasi) into every output component and runs Wizer to snapshot the JS heap with the user module pre-evaluated. The output is a 10–30 MB component that is ~99.99% engine and ~0.01% user code, and producing it takes minutes of CPU per route. For a mock that may only be hit a handful of times, this cost is wildly out of proportion to the work.

The framing that surfaced this: *we are already vendoring two JS engines* — V8 inside the Node binary in the sidecar image, and StarlingMonkey inside componentize-js — and using the first to bundle the second into each route's component. The decision is not "should we vendor a JS engine" (we already do) but "where does it live, and how often do we rebuild it?"

The same pattern generalises. Any interpreted handler language has the same shape: an engine plus a small program. The engine doesn't change per route; the program does. Coupling them at build time, as `componentize-js` does, is the cost driver.

Compiled-to-wasm AOT languages are a separate problem. Their compile cost is the compiler doing real work on the user's code, not bundling a runtime; it scales with handler size and is small for small handlers. Nothing in this ADR changes their story.

**Decision:**

WireMirage adopts a **shared wasm engine per interpreted language**. For each interpreted language we support, the host loads exactly one engine component at startup. Per-route artefacts are source bytes — not wasm.

Concrete shape for JavaScript / TypeScript (the only interpreted language in the tree today):

- A `js-engine.wasm` component is built **at cargo build time** by `crates/wm-host/build.rs`, which runs a pinned Dockerfile (`compiler/js-engine/Dockerfile` → `node:22-bookworm-slim@sha256:...`) and emits the artefact into cargo's `OUT_DIR`. `src/main.rs` `include_bytes!`'s the result via `env!("WM_JS_ENGINE_WASM")`. StarlingMonkey-based via componentize-js. Docker layer cache + cargo `rerun-if-changed` keep warm rebuilds at ~0 ms; only edits under `compiler/js-engine/` re-trigger the docker run. Nothing is checked in under `crates/wm-host/vendored/`. `WM_JS_ENGINE_WASM_OVERRIDE=/abs/path` bypasses docker for release-image multistage builds and no-Docker contributors. The component implements the `wiremirage` WIT contract and internally delegates `handle()` to JS source supplied at runtime.
- The component declares a host import along the lines of `wiremirage:host/handler.get-source: func() -> string`. Per request, the host's implementation returns the JS source for the matched route — already stored on the `Route` record since slice 36.
- Source routes need a transpile step before they can be handed to the engine. **The implementation uses pure-Rust `swc` in the host process** (the `wm-transpile` workspace crate, per [0038-one-transpiler-tsc-as-checker.md](0038-one-transpiler-tsc-as-checker.md)). The original sketch was to ship `swc-wasm` or `esbuild-wasm` *inside* the engine component; in practice both `sucrase` and `tsc`-on-StarlingMonkey tripped wasm `unreachable` traps inside the engine, so we lifted the transpile out of wasm entirely. **Both source languages go through it**, TypeScript and JavaScript alike: plain JS is valid TypeScript input, and the step is not only about erasing types — it also unwraps the module's exports into the script shape the engine's wrapper requires, which JS needs exactly as much as TS does. Per route, the host validates the source through swc at create/patch time and stores **the author's original source** on the `Route` record; the engine-runnable JS is derived from it at dispatch and cached (keyed by route id, evicted on update/delete). Storing the original is what lets `show_route_source` and `export_group` return what was actually written. **No Node, no runtime Docker, no network hop for JS/TS handlers.**
- The `compiler/typescript/` sidecar is **deleted** entirely. AOT languages still get sidecars per [0004-multi-language-via-sidecars.md](0004-multi-language-via-sidecars.md) when they arrive; the sidecar pattern is preserved for the workload it's appropriate for.

Adding a new interpreted language is: vendor an engine component for it (a Python engine, a Lua engine, a Ruby engine), implement the same `get-source` import, hook it up to a new `language` enum value. Once the JS pattern is established, additional interpreted languages are mostly mechanical.

**On type checking:** [0007-typescript-first.md](0007-typescript-first.md) commits to running `tsc` in the compiler sidecar at create time, on the argument that type checking is the agent's main feedback loop for handler correctness. That argument no longer holds. The dry-run facility (slice 32) already exercises handlers against synthetic input — including with seeded state (slice 33) — and surfaces semantic errors that type checking can't see ("returns 200 but no body", wrong content-type for the body it actually returned). For mock handlers — small, single-purpose, trivially exercised — *write → dry-run → iterate* is a strictly better feedback loop than *write → wait-for-tsc → iterate*.

Further: type checking at handler create time is a **TypeScript-specific** concern. JavaScript, Lua, Ruby, Perl, and Bash have no static typing at all. Python's `mypy`/`pyright` exist but conventionally run as CI/editor tools rather than load-time gates. Building a generic "every interpreted language gets a type-check gate" capability into the engine framework would be over-engineering for an affordance most languages don't expect.

v1 of this ADR therefore ships **transpile-only** via `swc-wasm` or `esbuild-wasm`. No `tsc`. The `.d.ts` generation from ADR-0007 is kept as an LSP/editor artefact — it costs nothing at create time and benefits both Ace and the agent's editor context. If, with measurement (or actual agent failure modes that dry-run doesn't catch), type checking earns its way back in, the cheapest path is `tsc`-in-the-vendored-JS-engine — tsc is itself JS and the engine is already there.

**On resource limits:** [0002-wasm-sandbox.md](0002-wasm-sandbox.md) commits to fuel + memory + epoch limits and slice 46 set them at 10 B fuel, 100-tick epoch (~1 s wall), 64 MiB memory. Those numbers were chosen for an already-snapshotted JS heap with no engine startup cost in the request path. With the shared-engine shape, the engine instantiates and parses source inside the request budget, so the same numbers will trip on every request.

Per the user's framing, the threat model in scope is **accidental infinite loops, not adversarial handlers**. WireMirage runs on trusted networks; the handler authors are the same team running the host (and increasingly, AI agents working on their behalf). Tight limits buy little here and cost a lot in surprise failures. The decision is to **widen the limits substantially and tighten only when measurement justifies it.** Starting values, to be refined during implementation:

- Fuel: removed for interpreted-language routes (epoch is the runaway-loop backstop). Kept for AOT routes where the budget can be tuned to actual program shape.
- Epoch: ~30 s wall clock. Long enough that "engine boots, parses 500 LoC of JS, runs the handler" never trips it on a non-pathological route. A `while(true)` loop still dies in 30 s.
- Memory: 256 MiB. Comfortably fits an engine instance plus a generous handler plus state.

These are starting points, not commitments. Re-tighten under measurement once we have flamegraphs.

**Consequences:**

- **`compiler/typescript/` runtime Docker dependency is removed.** Host has no *runtime* dependency on Node or Docker for the JS/TS path. `WM_COMPILER_URL` is **deleted** outright (not "kept for AOT-language sidecars" — when those arrive they will follow the engine pattern, not the sidecar pattern). Docker becomes a **build-time** dependency: `cargo build` invokes `compiler/js-engine/Dockerfile` to produce the engine bundle. The runtime image carries the embedded engine and never touches Docker. Build-time-only is materially different from the sidecar shape we're walking away from — it has no operational footprint, no network traffic, no separate process lifecycle.
- **Per-route create time drops from minutes to milliseconds** for JS/TS. The work is: optional TS→JS transpile (ms), validation, write to Valkey.
- **Per-route memory footprint drops from ~10–30 MB to source-bytes.** The host's RouteTable cache used to hold N JS-engine copies; it now holds N source blobs against one shared component handle. With a hundred routes, this is the difference between 1–3 GB and ~100 MB resident.
- **Per-request cost shifts.** The engine now instantiates and parses source inside the dispatch budget. Slice 46's fuel/epoch numbers will need bumping (see resource-limits section above). For workloads with steady-state traffic against a hot route, this is a real regression versus the snapshot model; an `Instance` cache or pre-parsed-bytecode store is the lever to pull if/when measurement shows it matters.
- **Handler type checking is intentionally not part of v1.** ADR-0007's "type checking gates handler create" framing is walked back here on the grounds that dry-run is the better feedback loop and a type-check gate is TS-specific rather than a generic interpreted-language capability. The `.d.ts` LSP hint from ADR-0007 is retained. ADR-0007 should grow a "type-checking gate is deferred per ADR-0020" header when this ADR lands.
- **Upstream-tracking burden.** The engine component is a build artefact we now own. Updating StarlingMonkey or componentize-js is a pinned-image bump in `compiler/js-engine/Dockerfile` plus `package-lock.json`; bumping `swc` is a Cargo.toml dependency edit. Both are routine. Acceptable — we already vendor StarlingMonkey transitively via componentize-js, just less hidden than before.
- **WIT contract and slice-46 sandbox are preserved.** The engine is a wasm component; the user's code runs inside it; wasmtime's resource limits still apply (just at wider settings). The "agent-native, multi-language, wasm-sandboxed" identity is intact.
- **[0004-multi-language-via-sidecars.md](0004-multi-language-via-sidecars.md) is partially superseded.** The "every language is a sidecar" universal is no longer true. The intent — host stays small, adding a language is mechanical — is preserved; the mechanism is now language-class-aware. ADR-0004 should be updated with a "Partially superseded by ADR-0020 for interpreted languages" header when this lands.
- **`Route.source` is no longer optional for interpreted-language routes.** Today the field is optional because some routes are pre-compiled wasm uploads. For `language: "typescript"|"javascript"|"lua"|...` the source is the artefact, so storing it is no longer just for the slice-36 viewer — it's load-bearing. Pre-compiled wasm uploads (`language: "wasm"`) keep working unchanged.

**Alternatives considered:**

- **Status quo (`componentize-js` per route).** Rejected. The cost — minutes of CPU, 10–30 MB per route — is the problem we're solving.
- **Run JS handlers in the Node sidecar via `vm.runInContext` instead of compiling to wasm at all.** Solves create-time, drops the wasm sandbox for JS routes. Node's `vm` module is famously not a security boundary; relying on it would create an asymmetry where JS routes are less-isolated than TinyGo routes. Rejected on uniformity grounds even though our threat model could probably absorb it.
- **Embed `rquickjs` (or similar) in the Rust host; run JS natively without wasm.** Identical trade to the previous bullet, plus pulls a JS engine into the host process address space. Rejected for the same reason — asymmetric sandbox story.
- **Drop wasm entirely; embed `mlua` and make Lua the only handler language.** Considered seriously. Gives zero compile cost, smallest possible deployment, mature Rust embedding. Rejected because (a) it gives up the multi-language identity that motivated [0003-component-model.md](0003-component-model.md), (b) Lua has materially lower LLM fluency than TS/Python per [0007-typescript-first.md](0007-typescript-first.md), (c) it would invalidate [0002-wasm-sandbox.md](0002-wasm-sandbox.md)'s sandbox-by-default property for a single-engine win. **Worth noting:** the shared-wasm-engine shape gets *most* of what mlua would have given us (zero per-route compile, source-bytes-only artefact, tiny per-route memory) while keeping the wasm sandbox and the multi-language path. mlua remains attractive only on the narrow argument of "no wasm overhead at runtime," which is much weaker than the create-cost argument.
- **Patch a wasm custom section per route instead of using a host import.** Same end-state (one engine, source per route) but at the byte level — each route gets its own component bytes with source inlined into a known custom section. Cheap to build but every route still produces a distinct `Component` in the wasmtime cache, losing the shared-component memory win. Rejected unless WIT-import overhead per request shows up as a measurable cost.
- **Run AOT compilers inside wasm too (`rustc-in-wasm`, `tinygo-in-wasm`).** Tempting for symmetry — no host-side toolchain at all. LLVM-in-wasm exists as a research project but is slow and memory-hungry, and `wasm-tools component new` would also need a wasm port. For Rust/TinyGo specifically, today this is a research project, not engineering. Zig is plausible but Zig isn't on the roadmap. AssemblyScript's compiler is already JS and so comes essentially for free once the JS engine is vendored — worth noting but not a v1 commitment.

**Implementation order:**

Each slice is shippable on its own. Slice A delivers the create-time win; B deletes the sidecar; C tightens the limits.

1. **Slice A — JS engine component + source dispatch.** Build (or vendor) `js-engine.wasm`. Add the `get-source` host import. New `language` handling path: store source, dispatch through the shared engine. Bump fuel/epoch/memory per the resource-limits section. Pre-compiled `language: "wasm"` uploads keep working unchanged. The Node sidecar still exists at this point; the `componentize-js` path is just no longer called for `typescript`/`javascript` source.
2. **Slice B — in-host TS→JS transpile.** Originally drafted as "add `swc-wasm` or `esbuild-wasm` as a second vendored component"; shipped as **pure-Rust `swc` called from `crate::ts_transpile`** in the host process. Sucrase and tsc baked into the StarlingMonkey component were tried first and both trapped at wasm `unreachable` (the latter at Wizer init). The host-Rust path side-steps StarlingMonkey entirely. Heavier dep tree, but reliable. **`compiler/typescript/` and the `WM_COMPILER_URL` env var are deleted**; `just test-sidecar` and `just build-sidecar-image` are gone.
3. **Slice C (delivery) — engine moves from vendored blob to cargo-build-time artefact.** Landed alongside the slice-A/B work. `crates/wm-host/build.rs` invokes `compiler/js-engine/Dockerfile` (pinned `node:22-bookworm-slim` by digest); the wasm lands in `OUT_DIR` and is embedded via `include_bytes!(env!("WM_JS_ENGINE_WASM"))`. Docker becomes a build dependency. Motivation: a 12 MiB blob per language committed to git doesn't scale once TinyGo or other engine-shaped languages arrive, and git pack bloat from engine.ts edits compounds with every iteration. The vendored-blob shape lived briefly in slices 56–58 and was excised by `git filter-repo` on the unpushed branch.
4. **Slice D (measurement) — limit tightening under traffic.** Once real traffic exists, instrument fuel and wall-clock per-request, then narrow the limits to actual observed shape plus headroom. ADR-0002 stays the home for the binding policy; this ADR's numbers are starting points. Was originally "Slice C — measurement and limit tightening"; renumbered to make room for the delivery refinement above.

The `Engine`-instance-cache and pre-parsed-bytecode optimisations stay deferred until measurement says they're needed. (The pre-parsed-bytecode half was subsequently built on exactly that trigger — see the 2026-05-27 amendment at the top. The `Engine`-instance cache is still deferred.) Type checking, if it earns its way back, ships as an opt-in TypeScript-only feature per the type-checking section above, not as a generic slice.
